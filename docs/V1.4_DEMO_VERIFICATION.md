## Capture boundary

The managed browser's filesystem read/write guard policy disables native `showSaveFilePicker` and `showOpenFilePicker`. The recording therefore uses the same isolated, in-memory picker boundary as `e2e/acceptance.mjs`, with a new empty fictional project. The application itself performs creation, serialization, autosave and Save Now through its normal Project File Service. The resulting serialized bytes were exported to a disposable local `.pmp` and inspected. No existing user project was opened or overwritten.

This verifies the application save flow and resulting file contents, **not native OS picker consent or direct disk writes by the browser**. The demo does not show an OS dialog. Native picker acceptance remains a manual check in a browser that permits filesystem access. There are no cloud data dependencies.

The production brief requires five assigned Task owners, but the baseline Tasks UI exposed no Owner control despite existing domain/persistence support. The user explicitly authorised adding that control. The change adds an optional creation selector and an inline selector, displays a retained deleted owner as inactive, and excludes deleted People from new selections. Table column sizing accommodates Owner. Browser coverage checks assignment to a newly created Person, Person rename and save/close/reopen persistence.
