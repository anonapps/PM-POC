# UI reuse matrix — compatibility completion

Date: 29 October 2026 (Europe/Madrid). Authority: [project requirements](PROJECT_REQUIREMENTS.md). Read with the [component contracts](UI_COMPONENT_CONTRACTS.md), [token inventory](UI_TOKEN_INVENTORY.md), [style ownership map](UI_STYLE_OWNERSHIP.md) and [migration evidence](UI_STANDARD_MIGRATION_PLAN.md).

This matrix completes the source-level inventory of the remaining table, validation and overlay families. It records reuse boundaries; it does not claim every literal or selector has migrated, every visual state has been measured, or every platform has been manually accepted. Current computed values and test evidence remain in the audit/migration records. Historical overrides are not deleted merely because a newer declaration has a similar name.

Classification:

- **Same:** an existing shared asset owns the behavior or native composition. Reuse that export and its context variant.
- **Similar:** the visual purpose overlaps, but content, state, ancestry or geometry differs. Reuse the common kernel; preserve the adapter.
- **Distinct:** different semantics or interaction require a separate recipe. Matching numbers/colors do not make these duplicates.

### Reviewed simplifications and retained message variants

Three conditional duplicate-name notices share `small.field-warning[role=status]`, but the production strings and conditional state remain module-owned. They are a potential small semantic helper only when a consumer needs change; creating a second general message abstraction solely to wrap three short nodes is not required for this compatibility inventory.

Task's existing conditional date error could compose FieldMessage only while retaining the outer error condition, `field-error` class and exact ID; that would add no visual standardization benefit by itself. The Gantt variant has a different class contract. Do not substitute the default reserved-error variant blindly.

The legacy `CreationField` export in `src/features/shared/creation-field.tsx` had no production/catalogue imports or JSX consumers and is retired in this closeout. Similarly named `CreationFieldErrors` types are live and unrelated. Current forms use FormField/EntityCreationPanel. Removing the unused helper does not establish that the old CSS error recipe is globally unused.

## Completion boundary and future changes

This inventory is complete when each listed family has a real source, reuse path, consumer class and reason for retained differences. Compatibility consolidation is complete for a candidate only after exact source/native-contract equivalence or before/after computed-style evidence and affected behavior checks. Final regression and local review evidence belong in the migration plan, not implied by the matrix itself.

The remaining items are deliberate boundaries, not an indefinite requirement to wrap every cell, replace every literal or eliminate every local selector. A future change starts with a concrete consumer; reuse the existing kernel and context variant first. Add a component/token only when it owns a meaningful repeated contract. Remove a legacy declaration only after every consumer and cascade consequence is accounted for. Keep source generation fresh and the catalogue tied to actual shared assets.

For a new table or form: choose the closest real catalogue example; keep validation/domain/file actions outside presentation facades; retain native headings/selection structure; exercise long/empty/deleted/disabled/invalid and narrow states; document intentional exceptions. Visual normalization and native-platform acceptance remain explicit decisions, separate from this source-level inventory.
